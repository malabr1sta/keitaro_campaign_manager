Keitaro Wrapper · спецификация бэкенда

Граница приложения

FastAPI обслуживает HTML и собственные JSON-маршруты /api. Только сервер обращается к Keitaro Admin API. В routes.py оставить HTTP и валидацию, в campaign_service.py — создание и редактирование, в keitaro_client.py — транспорт, тайм-ауты, отображение полей конкретной версии. models.py и db.py отвечают за локальное состояние. Правило пересчёта долей оформить чистой функцией с табличными тестами. SQLAlchemy и Alembic работают с локальной БД. Сервер трекера — источник истины о конфигурации.

Подключение

KEITARO_BASE_URL — адрес установки, KEITARO_API_KEY — секрет серверного процесса, KEITARO_DOMAIN_ID, KEITARO_GROUP_ID, KEITARO_TRAFFIC_SOURCE_ID — существующие записи стенда. DATABASE_URL — локальная БД. В .env.example оставить примеры без действующих ключей. Клиент добавляет /admin_api/v1 и заголовок Api-Key, применяет конечные тайм-ауты. URL кампании для посетителя и адрес Admin API могут иметь разные домены.

Карта обращений к Keitaro

Задача

Внешний метод относительно /admin_api/v1

Списки кампаний и офферов

GET /campaigns, GET /offers

Открыть кампанию, получить её потоки

GET /campaigns/{id}, GET /campaigns/{id}/streams

Проверить настроенные справочники

GET /domains, GET /groups?type=campaigns, GET /traffic_sources

Создать кампанию и поток

POST /campaigns, POST /streams

Прочитать или обновить выбранный поток

GET /streams/{id}, PUT /streams/{id}

Сверить имена фильтров и действий

GET /stream_filters, GET /streams_actions

Контракт записи сверить с документацией в профиле именно целевой установки. В публичной схеме создания кампании обязательны name и alias. Передать type=position, domain_id, group_id и traffic_source_id. Учесть, что в публичной схеме group_id для создания описан как строка. Для создания потока требуются campaign_id, schema, type, name, action_type. Определить реальные значения action_type, способ передачи URL и формат country-фильтра на тестовом стенде. Сопоставить с эталонным запросом интерфейса через DevTools → Network → Fetch/XHR → Payload. Сохранить очищенные образцы как фикстуры. В ответах Keitaro встречаются служебные поля и отличия типов от запроса. Формировать тело записи из разрешённых полей.

Источники для проверки — Admin API Reference, руководство по работе с Admin API, приоритет потоков.

Порядок выдачи согласовать с визуализацией в FRONTEND-SDD.md.

Создание

Очистить название от крайних пробелов. Проверить непустую строку, существующий код ISO 3166-1 alpha-2 в верхнем регистре, положительный ID и доступность оффера. Проверить конфигурацию домена, группы кампаний, источника до первой записи в трекер.

До внешнего вызова сохранить операцию с уникальным ключом запроса, отпечатком ввода и стабильным уникальным alias. Создать кампанию. По возможности сначала создать выключенной и включить после проверки, сверив операцию включения на стенде.

В рамках новой кампании задать два обычных активных потока с явной очередностью. Первый принимает только выбранную страну, назначение https://www.google.com/. Второй без фильтров использует существующий оффер с долей 100. Параметры редиректа и схемы для офферов брать из проверенных образцов стенда.

После каждого шага короткой локальной транзакцией сохранить полученный remote ID и стадию. Перечитать настройки и потоки, подтвердить порядок, фильтр, URL, ID оффера, долю и конечное активное состояние. После этого показать успех.

Таблица creation_operations: id, уникальные request_key и alias, input_hash, исходные name/country_code/offer_id либо JSON запроса, stage, campaign_id, geo_stream_id, offer_stream_id, last_error, created_at, updated_at. Миграция создаёт таблицу и ограничения. Не держать транзакцию БД открытой во время HTTP-вызовов.

Повтор с тем же ключом и другими данными → 409. Один исполнитель на операцию. После тайм-аута записи сначала найти созданную кампанию по сохранённому alias либо сопоставить поток в известной кампании по сохранённому ID/проверенной конфигурации. Продолжать только однозначно установленный шаг. При неоднозначности вернуть operation_id, текущий статус и понятное сообщение. Два POST подряд вслепую могут создать дубликат.

Редактирование потока

Перед записью получить поток, сверить campaign_id, тип назначения и revision. Для одного процесса сериализовать изменения одного sid, в том числе проверку и запись. revision — отпечаток редактируемого состояния (набор связей, порядок, доли, состояния и настройки, влияющие на доступность редактирования). При изменении через другую вкладку вернуть 409 с предложением перечитать. Это снижает риск устаревшей записи. Внешний редактор может вмешаться между чтением и PUT; без подтверждённой поддержки условной записи трекером полной межсистемной блокировки нет.

При добавлении взять актуальный список, проверить существование нового offer_id и отсутствие дубля. При удалении исключить только связь с указанным offer_id. Пересчитать доли по согласованной политике. Передать в PUT /streams/{sid} новый список offers с offer_id, share и state. На стенде убедиться, что частичный запрос сохраняет опущенные поля; если версия требует дополнительные данные, копировать требуемые записываемые настройки из свежего ответа. Проверить сохранность фильтров, лендингов, действий, соседних потоков и глобальной записи оффера. После записи перечитать и вернуть результат. При тайм-ауте сначала проверить фактический состав.

Временная политика до просмотра видео

Для обычного потока с активными офферами взять равное распределение при изменении состава. Для N активных строк разделить 100 на N нацело, остаток раздать по одному в сохранённом порядке. Новый оффер идёт в конец. Примеры: A → A/B = 50/50; A/B → A/B/C = 34/33/33; удалить B → A/C = 50/50. Открытие потока 70/30 само по себе оставляет 70/30. Последний активный оффер временно запрещено убирать. Потоки с выключенными связями показывать с их реальными данными; до уточнения политики ограничить изменение состава такого потока с пояснением. Если видео требует иного поведения, заменить политику, состояния кнопок и эталонные тесты. Эти решения не являются ограничениями Keitaro.

Ошибки и проверки

Единый ответ об ошибке: {code,message,field_errors?,operation_id?,campaign_id?}. 422 — ввод или невозможное изменение состава; 404 — отсутствующая кампания/поток/связь; 409 — конфликт версии, дубликат или операция уже выполняется; 502/504 — ошибка вызова или тайм-аут зависимости. Недоступность API для ключа/редакции объяснять как проблему настройки подключения. Секреты и сырые трассировки исключить из ответа.

Проверки сервиса: обе страны; два потока в правильном порядке; дублированный POST; потеря ответа после создания кампании и после создания потока; существующая кампания без локальной истории; поток другой кампании; повторный оффер; алгоритм долей и последний оффер; конфликт двух вкладок; сохранение настроек при PUT. Клиент проверять с httpx.MockTransport на обезличенных ответах. Живую проверку выполнить отдельно и явно отметить её результат в README.
